Mockup for review: the intake run as a live card

Today the page greys out while a message is read, the only signs of life are the Send button's spinner and a small pulsing line, there is no way to stop or change anything, and a 120 s model timeout kills the whole turn. In this design the message lands in the thread at once, a run card under it shows each step with its time, cards appear per item as they finish, you can stop the run or pull the message back to edit, the composer stays open (a second message queues), and a timed-out call is retried up to three times on its own. What changes under the hood: the run's progress becomes a stream of events (step, item, attempt, elapsed, cards of a finished item) that the thread, the list row and the nav badge all read, so leaving the page never loses it; a model call that times out or gets a 5xx/429 is retried on its own (attempt 2 same tier, attempt 3 fast tier, short pauses between), and only then does the turn fail; the cards of each item are written as that item finishes, so a failure or a stop keeps what was done; Stop and Edit cancel the calls in flight; the composer never greys out, and a message sent during a run waits for it, as does a note added from the run card.

Open questions for you
  • A message sent while a run is going: queue it behind the run (as here) or start a second run at once?
  • Edit during a run: stop and put the text back in the box (as here), or keep the run and apply the edit afterwards as a follow-up?
  • Retries: attempt 3 on the fast tier (as here) or all three on the same tier?
  • The step list: always shown (as here) or a plain spinner for the first 5 s and the list only when it takes longer?
  • Per-call timeout stays 120 s? It is a setting today; a shorter one (60 s) with three attempts fails faster on a stuck provider.
