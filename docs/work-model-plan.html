The proposal

A work model, and everything reads from it

Inputs become events. Events update a state per work item. Rules read the state and produce outcome cards. Intake, chat, the ticket view and Today read the same state.

Work items with an event log

Event log
  • A local table for pieces of work in flight. Each one is a group of the tickets that serve one goal, built by code from links, epics, shared waits and what arrives together; often a single ticket, by default not limited to one.
  • Every input and change becomes an event.
  • Code attaches events by ticket key, thread, owner and names. It asks only when it cannot tell.

A state kept current

Work item state
  • After each event the state updates in a fixed schema.
  • One narrow model call folds the new event into the previous state. That is its only job.
  • Code checks the result against the facts it holds and rejects invented dates or people.
  • The state shows on the ticket and on Today as a short status note you can edit. Your corrections are learning.

Consequence rules

Rules
  • Deterministic rules over the work model. Each one produces proposals or an outcome card.
  • Expected date moved. Update the wait, dependent due dates and anyone owed an ETA.
  • Blocker closed. Resume, and say so on the ticket.
  • A commitment is due today.
  • A teammate changed your ticket. Read it. Is a reply owed?
  • A wait went unanswered past the chase interval.
  • Each rule has a switch. Reject a rule twice on the same work item and it goes quiet there.

Suggestions where you are

Ticket view and Today
  • Open a ticket, start a draft, or say "I'm on PAY-12 now". You see that work item's state and next moves, ranked against sprint and dates.
  • New input that arrives mid-task is triaged against your current work. Either it changes what you are doing, or it is parked with a reason and comes back when you finish.

Your call

Two questions only you can answer

A

Should a work item default to one per active ticket?

Decided 18 Oct: no. A work item is a group from day one. Code builds the group from epic and parent, blocks and relates links, shared waits and requesters, and tickets named together in one paste or thread. The user splits or merges, and each correction is learning. State lives at the group level and shows on every ticket in it.

B

How much will you tell the app by hand?

"I'm on this now" and end-of-day answers, versus letting it infer from Jira activity and your views alone. Decided 18 Oct: both. Rick will give the app as much as he can, and the app must still infer from Jira activity, pastes, approvals and opened tickets on its own. When it is uncertain it asks a question instead of guessing.
