# Secretary: Design

Status: built. Approved for implementation 2026-09-23; all phases done by 2026-09-26.
Companion to `requirements.md` (what) and `implementation-plan.md` (when, now
history). Decisions taken during the build (section 12, D19–D28) override older
text; notes marked "Now:" point to them where the text below is out of date.

## 1. Architecture overview

Single-process Tauri 2 desktop app. All business logic runs in TypeScript inside the
webview, organised as Effect services. The Rust side is limited to Tauri plugins and
one tiny keychain command. No sidecar process.

```
+------------------------------------------------------------------+
| Tauri 2 shell (Rust)                                             |
|  plugins: http, sql (sqlite), store, clipboard-manager,          |
|           notification, opener, log, dialog, fs                  |
|  custom command: keychain get/set/delete (keyring crate)         |
+---------------------------^--------------------------------------+
                            | invoke / plugin JS bindings
+---------------------------v--------------------------------------+
| Webview (React 19 + TypeScript)                                  |
|                                                                  |
|  UI layer      shadcn/ui, TanStack Router, TanStack Query,       |
|                react-hook-form + zod                             |
|                                                                  |
|  App services (Effect)                                           |
|    Settings  Secrets  Db(drizzle)  Fetcher  JiraClient           |
|    ConfluenceClient  Llm(ai sdk)  Retrieval  Intake  Proposals   |
|    Executor  Sync  Comms  Learning  Chat                         |
|  Plain modules: dashboard (scoring, brief), dependencies,        |
|    directory, tickets, inbox, memory, sprints, data              |
|                                                                  |
|  Outbound HTTP via @tauri-apps/plugin-http fetch (no CORS);      |
|  the Fetcher lets through configured hosts only (D27)            |
+------------------------------------------------------------------+
        |                    |                     |
   Jira REST v2        Confluence REST         LLM endpoints
   DC: Bearer PAT      DC: Bearer PAT          (OpenAI-compat / Anthropic)
   Cloud: Basic        Cloud: Basic
   (email, API token)  (email, API token)
```

Now: Cloud as well as Data Center (D19); see the Cloud table in section 5.

Why no sidecar: a Bun sidecar would add process lifecycle, IPC and packaging work.
Everything needed (SQLite, HTTP without CORS, keychain) is available to the webview
through official Tauri plugins, and Effect and the AI SDK run fine in a browser
runtime. Bun is still used as package manager, script runner and test runner. If a
webview limitation appears later (for example a native SQLite extension), the Effect
service boundary lets a sidecar replace individual services without UI changes.

Rejected alternatives:

- Two official SDKs (`@anthropic-ai/sdk`, `openai`) behind a handwritten interface.
  Rejected: the AI SDK already provides that interface, structured outputs, tool
  loops and streaming, which matches the "mature libraries" rule. Anthropic-specific
  options (adaptive thinking, effort) are still reachable via `providerOptions`.
- Bun sidecar with Effect HTTP server. Rejected for v1 (see section 1).
- Vector embeddings for retrieval. Rejected for v1: the corpus is small (a few
  thousand issues, a few dozen contacts); FTS5 or LIKE plus LLM reranking is enough
  and avoids a dependency on an embeddings endpoint.

## 4. Data model (SQLite, drizzle)

JSON columns are typed with zod at the service boundary.

external-content FTS5 table over `jira_issues(key, summary, description)` kept in
sync by triggers; `context_notes` gets the same treatment in Phase 2. User text is
turned into a prefix query of quoted tokens by a pure function.

## 5. Jira Data Center integration

Auth: `Authorization: Bearer <PAT>`. Base path `/rest/api/2`. The Agile endpoint
under `/rest/agile/1.0` (board sprints, D23) is optional: a board the user cannot
read keeps the sprints its issues show. Cloud differences are in the table further
down.

Endpoints used (reads in `services/jira/live.ts`, writes built in
`services/executor/jira-mapping.ts`):

| Purpose | Endpoint |
|---|---|
| Test connection, current user | `GET /myself` |
| Field discovery (Epic Link, Epic Name, Sprint ids) | `GET /field` |
| Search (paged, `startAt`/`maxResults`=100) | `POST /search` with `jql`, `fields`, `expand: ["renderedFields"]`, `validateQuery: "warn"` |
| Issue read (single-issue sync, re-fetch after a write) | `GET /issue/{key}?fields=...&expand=renderedFields` |
| Comments | `GET /issue/{key}/comment` (paged, `expand=renderedBody`), `POST /issue/{key}/comment` |
| Transitions | `GET /issue/{key}/transitions`, `POST /issue/{key}/transitions` |
| Create | `POST /issue`; metadata from `GET /issue/createmeta/{project}/issuetypes` and `.../issuetypes/{id}` |
| Update fields, epic, parent | `PUT /issue/{key}`; `GET /issue/{key}/editmeta` decides between Epic Link and `parent` |
| Assignee | `PUT /issue/{key}/assignee`; picker `GET /user/assignable/search` |
| Priorities | `GET /priority` |
| Issue types and statuses per project | `GET /project/{key}/statuses` |
| Remote links (dependency mirroring, D18) | `POST /issue/{key}/remotelink` (upsert by `globalId`), `DELETE /issue/{key}/remotelink?globalId=...` |
| Board sprints (D23) | `GET /rest/agile/1.0/board/{id}/sprint` |

The client also wraps `GET /project` and `GET /issue/{key}/remotelink`; nothing
calls them yet. Issue links (`/issueLink`) and comment edits are not used.

Sync algorithm:

1. Scope JQL = user JQL (default
   `(assignee = currentUser() OR reporter = currentUser() OR watcher = currentUser()) AND updated >= -90d`)
   UNION children of tracked epics (`"Epic Link" in (KEYS) OR parent in (KEYS)`)
   UNION the tracked epics themselves.
2. Incremental: append `AND updated >= "<watermark minus 5 minutes>"` (format
   `yyyy/MM/dd HH:mm`), page through, upsert. Watermark = max `updated` seen.
3. Full resync weekly or on demand to catch deletions and scope changes: mark
   issues not returned as `stale` rather than deleting.
4. Comments come embedded in the search response (`comment` field); when an issue
   has more comments than were embedded, the rest are fetched from
   `/issue/{key}/comment`. Only issues returned in this run are touched.
5. Epic relation: read both `parent` and the discovered Epic Link field; write using
   whichever the edit or create metadata for that project/issue type accepts.
6. Sub-tasks of stories under tracked epics have no Epic Link, so a second pass
   queries `parent in (...)` for those stories in chunks of 100 keys.
7. JQL date literals are interpreted in the Jira user's time zone, so the
   watermark is formatted in `myself.timeZone`. Searches order by `updated ASC`
   and request `expand=renderedFields`; field ids for Epic Link, Epic Name and
   Sprint come from `/field` (schema.custom `gh-epic-link`, `gh-epic-label`,
   `gh-sprint`) unless overridden in settings.
8. Writes are bulk upserts per page (one multi-row statement for issues, one for
   comments) to keep IPC round trips low. Sync is idempotent, so a crash mid-run
   only means the next run repeats work. State lives in `sync_state`:
   `jira.watermark`, `jira.lastSyncAt`, `jira.lastFullSyncAt`, `jira.fields`,
   `jira.timeZone`, `jira.username`, `jira.projectMeta` (issue types and statuses
   per project) and `jira.sprints` (D23).

Jira Cloud (D19) differs only inside the client and payload mapping:

| Concern | Data Center | Cloud |
|---|---|---|
| Auth | `Bearer <PAT>` | `Basic base64(email:api_token)` |
| API root | configured URL incl. context path | site origin (`https://<site>.atlassian.net`) |
| Search | `POST /search` (`startAt`, `total`) | `POST /search/jql` (`nextPageToken`, `isLast`, no total; `expand` is a comma string); old `/search` returns 410 |
| Users | `name` | `accountId` (stored in the same columns) |
| Assign | `{name}` | `{accountId}`; create/edit field `{id}` |
| Epics | Epic Link field, else `parent` | `parent` only; remove with `update.parent[{set:{none:true}}]`; `hierarchyLevel` 1 = epic |
| Create metadata | `values` | `issueTypes` / `fields` |
| Priorities | `/priority` | `/priority/search` |
| Mentions | `[~username]` | `[~accountid:ID]` |
| Rate limits | - | 429 + `Retry-After`, retried up to three times (search included) |

Manual actions from the ticket view (comment, transition, edit fields, assign,
set epic) are user-initiated writes. They go through `Executor.run(action)`, the
same path approved proposals use in Phase 3: payload building in
`services/executor/jira-mapping.ts`, the request, an `actions_log` row, then a
re-fetch and upsert of the issue. Description edits are made in wiki markup, not
Markdown, because a wiki -> Markdown -> wiki round trip is lossy for panels,
macros and tables.

Write mapping (proposal -> request) lives in `services/executor/jira-mapping.ts` and
is unit-tested with fixtures. Description and comment bodies are converted from
Markdown to wiki markup before sending. After every write, the affected issue is
re-fetched and upserted so the UI shows Jira's truth.

## 7. LLM layer

### 7.0 Principles: deterministic first, model second

The secretary's behaviour must not change character when the user swaps models.
Rules that every pipeline follows:

1. **Code owns the facts.** Reference extraction (issue keys, INC numbers, names),
   candidate retrieval, ranking, payload building, date math, and validation are
   plain TypeScript with unit tests. The model never recalls a ticket key; it
   selects from candidates the code retrieved, or asks for a new issue.
2. **Narrow, schema-bound calls.** Each call answers one question with a zod
   schema. Long inputs are first split into atomic items (a cheap call), then each
   item is classified separately. Small, single-purpose calls behave far more
   consistently across models than one large "do everything" prompt.
3. **Constrained choices over free text.** Wherever possible the schema uses enums
   and candidate IDs (`target: 'ABC-123' | '$new:1'`, `team_id` from the supplied
   list) rather than free strings. Free text is limited to summaries, bodies and
   rationale.
4. **Validate, repair, escalate, then ask.** Every output is parsed and checked
   against the candidate set and business rules (issue type allowed for project,
   transition exists, contact exists). A failed check triggers one repair call with
   the validation errors, then one retry on the next stronger tier if escalation is
   on, then a "needs clarification" proposal. Nothing invalid reaches the UI.
5. **Few-shot from the user's own history.** Correction examples and approved
   proposals are the primary steering mechanism, which works on every model tier.
6. **Sampling is not the determinism lever.** Current Anthropic models reject
   temperature and related parameters; OpenAI-compatible endpoints get
   `temperature: 0` and a `seed` when the provider supports them. Consistency comes
   from the structure above, not from sampling settings.
7. **Measure per task.** Approved proposals form a replay set; the user can run any
   task type on any model and see the agreement rate (FR-9.4) before switching.

### 7.1 Provider abstraction and task routing

`Llm` service exposes `generateObject(schema, prompt, opts)`, `generateText`,
`streamText` and `runTools`. Now: `object(task, request)`, `text(task, request)`,
`stream(task, request)` (the chat tool loop), `test(target)` and `route(task)`; see
`services/llm/index.ts`. Underneath, a provider registry built from settings:

- `anthropic`: `createAnthropic({ baseURL, apiKey, fetch, headers })`. Default model
  suggestion `claude-opus-5`. Pass `providerOptions.anthropic` for adaptive thinking
  (`thinking: { type: 'adaptive' }`) and `effort` where the endpoint supports them;
  make both configurable per provider because Anthropic-compatible proxies may reject
  them. Handle the `refusal` finish reason explicitly: show the user a clear message,
  never retry silently.
- `openai-compatible`: `createOpenAICompatible({ name, baseURL, apiKey, fetch, headers })`.
  Structured output mode configurable (`json_schema` response format vs tool-call
  emulation) because compatible servers differ.

**Tiers.** Three slots, each bound to a provider and model: `fast`, `standard`,
`strong`. An unconfigured tier falls back to the next stronger configured one, so a
single configured model works everywhere. Suggested Anthropic defaults:
`claude-haiku-4-5` / `claude-sonnet-5` / `claude-opus-5` (now `claude-opus-5-5`).

**Task routing.** Every LLM task type declares a default tier; the user may
override per task. `escalate` marks tasks that retry once on the next stronger tier
when validation fails or confidence is below the task threshold.

| Task type | Default tier | Escalate | Notes |
|---|---|---|---|
| `segment_input` (split long paste into atomic items) | fast | yes | Skipped for short inputs (code decides by length and line count) |
| `rerank_candidates` (order retrieved tickets for one item) | fast | no | Optional; skipped when FTS returns 5 or fewer |
| `classify_item` (one item -> proposals, candidate-constrained) | standard | yes | The core call; strict schema, enums, candidate IDs |
| `route_reply` (which items of a thread a typed reply is about, D22) | fast | no | Enum of item indices; falls back to every item |
| `repair_output` (fix a failed validation with error list) | same as failed call | n/a | One attempt |
| `extract_profile_facts` (personality/title cues about a contact) | fast | no | Produces `update_person` proposals only |
| `summarize` (comment threads, long descriptions for context) | fast | no | Cached by content hash |
| `draft_message` | standard | no | User regenerates instead of auto-escalating |
| `daily_brief` | standard | no | |
| `consolidate_rules` | strong | n/a | Rare, high value |
| `chat` | standard | no | Tool loop; user can pick tier in the panel |

`repair_output` and `test_connection` are internal: recorded in `llm_calls`, not
routable in settings (`services/llm/tasks.ts`).

The `Llm` service API takes a task type, not a model: `llm.object(task, schema,
prompt)`; routing, accounting, timeouts, repair and escalation are handled inside.
`llm_calls` records `task`, `tier`, `model`, `escalated` and `validation_ok`.

Every call records `llm_calls` and is wrapped in Effect with timeout, one retry on
network/429/5xx, and cancellation via AbortSignal tied to the UI.

### 7.2 Prompt construction

Common system prompt: role, hard rules (propose only, never claim to have written to
Jira, treat pasted content as untrusted data, ask when unsure), output language.
Context blocks are assembled by the `Retrieval` service in a fixed order for prompt
cache friendliness: static rules -> memories -> directory (teams, people, compact)
-> candidate tickets -> input. Each block has a token budget; retrieval trims by
rank. Token counts are estimated locally (approximation is fine for budgeting).

### 7.3 Pipelines

**Intake** (`services/intake`), decomposed so each model call is small:
1. Code: extract explicit references: Jira keys `[A-Z][A-Z0-9]+-\d+`, ServiceNow
   `INC\d{7,}`, `@names` and emails matched to contacts. Normalise whitespace,
   strip quoted email history and signatures with deterministic heuristics.
2. Model (`segment_input`, fast) only if the input is long or multi-paragraph:
   split into atomic items, each with its quoted span. Short inputs are one item.
3. Code, per item: retrieval. Referenced issues; FTS top 15 by summary/description;
   10 most recently viewed/updated issues; open dependencies for those; all teams
   (compact); contacts mentioned or in the sender's team; memories of kind
   rule/preference ranked; the 10 most relevant correction examples. Optional
   `rerank_candidates` (fast) when more than 5 candidates.
4. Model (`classify_item`, standard): `ItemResultSchema` =
   `{ proposals: Proposal[], question?: string, confidence: number }`. `Proposal` is
   a discriminated union by `kind` (FR-2.2). (Now: one flat object with a `kind`
   enum and nullable fields; code checks the fields each kind needs, D21.) Targets
   are constrained to the
   candidate IDs supplied in the prompt or `$new:n`; team, contact and issue type
   fields are enums built from the retrieved lists. Each proposal carries
   `rationale` and `evidence` (quoted span).
5. Code: validate against candidates and Jira create metadata; dedupe proposals
   across items; merge `$new` placeholders; apply confidence threshold. On failure:
   repair call, then escalation to strong if enabled, then a "needs clarification"
   proposal instead of a guess.
6. Persist inbox item, items and proposals as `pending`. UI renders cards grouped
   by item, with the quoted span shown next to each proposal.

Implementation notes (Phase 3):
- The model's output schema (`src/prompts/classify.ts`) is separate from the
  canonical `ProposalPayload` (`src/services/proposals/schema.ts`). Code maps one to
  the other, so prompts can change without touching stored proposals or the Executor.
- Output schemas use nullable fields (never optional) and no numeric bounds, because
  strict structured-output modes differ across providers; confidences are clamped in
  code.
- `rerank_candidates` is not called: deterministic merging of mentioned, bm25, sender,
  recent and tracked-epic candidates within a token budget was enough. The task type
  stays in the routing table for later use.
- If segmentation fails validation after repair, the whole cleaned text is classified
  as one item rather than asking the user.
- A needs-clarification card takes the user's answer and re-triages the original input
  with the answer as a separate, trusted prompt block; the question is then closed.
  (Now: the answer is a reply in the thread and revises only the item that asked,
  D22; see Threads below.)
- Proposal execution resolves `$new` refs from creates already executed in the same
  inbox item; a proposal whose create failed or is still pending fails with a clear
  message instead of running.

**Threads** (D22, `Intake.reply`)
- A message holds typed text and pasted blocks. The composer turns every paste into
  a pasted block (untrusted, labelled by source); the user can convert a block to
  their own words. In the first message, pasted blocks are the input and typed text
  is a trusted instruction; with no pasted block, the typed text is the input, as
  before.
- A reply with pasted blocks adds new items (segmented if long) that the reply's
  typed text instructs; existing items are untouched. A reply with only typed text
  revises existing items: an answer to a question goes to the item that asked; with
  one item it goes to that item; otherwise `route_reply` (fast, enum of item indices)
  picks the items, falling back to all of them. Items whose pending proposals use a
  `$new` ref created by a revised item are revised too.
- A revised item is classified again with a thread block: every instruction so far
  (trusted), its pending proposals in the output schema's shape, and decided
  proposals (done or rejected; not to repeat). The model returns the complete
  pending set. The old pending proposals become `superseded`, and one correction
  example records the instruction with the before and after sets.
- New `$new` refs are numbered after refs used by decided creates in the thread;
  issues created earlier in the thread are candidates by key.

**Executor** (`services/executor`)
Approve -> `edited_payload ?? payload` -> Jira/DB action -> re-fetch -> `actions_log`.
Rejection and edits both create `memories` of kind `example` (FR-7.2). Executes
sequentially so a created issue's key can be referenced by later proposals in the
same batch (`$new:1` placeholders resolved at run time).

**Scoring** (`services/scoring`, pure functions, unit-tested; now
`services/dashboard/scoring.ts`, see below)
`score = w_pri * priorityWeight + w_due * dueProximity + w_block * blocked
       + w_stale * staleness + w_dep * overdueDependencyDays + w_pin * pinned
       + override`
Weights in settings with defaults. Returns the score and a list of reasons.

Implementation (Phase 5, `services/dashboard/scoring.ts`): each factor is scaled to
0..1 before weighting. Priority maps Jira names (Highest/Blocker 1 ... Lowest 0.1,
none 0.4); due proximity is 1 when due or overdue and falls to 0 two weeks out;
blocked is 1 when an open issue blocks it, its status reads blocked/on hold, or a
dependency is blocked; blocking scales with blocked issues (full at three); staleness
starts after 7 idle days and is full at 30; the dependency factor is full at 7 days
overdue; pinned is 1. The local override is added as points. Defaults: priority 3,
due 4, blocked 2, blocking 2, stale 1, dependency 3, pinned 10 (Settings > Ranking).
Top focus covers open, non-epic issues that are assigned to the user, pinned, under a
tracked epic or have an open dependency, minus snoozed ones.

Brief implementation: code collects the facts (changes since the last brief, top
focus with reasons, due soon, overdue dependencies, follow-ups due, waiting on me,
pending proposals) and `daily_brief` returns three Markdown sections through
`llm.object`, validated so every overdue dependency, the first due-soon items and the
first focus items are named; a failed check goes through repair and escalation. The
brief is cached in `sync_state` with a hash of the facts and is shown as out of date
once anything changes; with nothing to report no model call is made.

**Brief** (`services/dashboard/brief.ts`): see the brief implementation paragraph
above. It is one schema-bound `llm.object` call, not free text, and the cache key is
a hash of the facts, not table changes.

**Comms** (`services/comms`, D24) one `llm.object` call (task `draft_message`)
producing `{ subject?, variants: { short, standard } }` from intent, recipient profile and
team, linked tickets (summary, status, last change), dependency history, last 3
communications to the recipient, memories about the recipient, output language.

**Memory consolidation** (`services/memory`) on request: groups examples by
proposal kind and subject, asks the strong tier for candidate rules, presents
them as `remember_rule` proposals. (Now: `Learning.consolidate` in
`services/learning`, producing `remember` proposals in a new thread, D26;
`services/memory` holds the Memory page queries.)

**Evaluation replay** (`services/eval`, Should) selects inbox items whose
proposals reached `executed`, re-runs `classify_item` with a chosen tier or model
on the stored retrieval snapshot, and reports exact-match and kind-match rates per
proposal kind. Retrieval snapshots are stored on the inbox item at triage time so
replays compare models, not data drift. (Now: `Learning.replay` in
`services/learning`, comparing kind and target with what the user approved, with
scoring in `services/eval/score.ts`; snapshots are stored per intake item in
`intake_items.snapshot`, D26.)

**Chat** (`services/chat`, Should) AI SDK tool loop with read tools
(`searchIssues`, `getIssue`, `listDependencies`, `searchPeople`, `searchConfluence`,
`listMemories`) and one write tool `propose(proposals)` that only inserts pending
proposals. Step limit 8. (Now, D25 and D28: the tools in `services/chat/tools.ts`
are `search_tickets`, `get_ticket`, `waiting_on`, `find_contacts`, `search_notes`,
`my_focus` and `search_confluence`, plus `propose_actions`, which sends the request
through intake as a new thread instead of inserting proposals itself.
Conversations are saved in `chat_conversations`.)

## 9. Security and privacy

- PAT and API keys: OS keychain only. Settings store holds non-secret config.
- Tauri capabilities: `http:default` open to http(s); the `Fetcher` only lets
  requests through to configured hosts (D27). `sql`, `store`,
  `clipboard-manager:allow-write-text`, `notification`, `opener` for external links
  only, `fs` text files for chosen export and import paths.
- CSP restricts scripts to self. No remote code.
- Logging redacts `Authorization` and `x-api-key` headers and any value stored as a
  secret.
- Exports exclude secrets. Imports validate with zod.
- Pasted content is wrapped in delimiters and labelled untrusted in prompts; the
  approval gate is the primary control.

## 10. Error handling

Effect typed errors per service: `JiraError{kind, status?}` (kind:
not_configured|auth|http|network|timeout|decode), `ConfluenceError`,
`LlmError{kind: config|auth|network|rate_limit|refusal|schema|timeout|cancelled|provider}`,
`DbError`, `SecretsError`, `SettingsError`, `SyncError`, `IntakeError`,
`ProposalError`, `ExecutorError`, `CommsError`, `LearningError`, `TransferError`. UI maps each to a toast with a retry or a settings link.
No silent fallbacks between providers; the user chooses the model.

## 11. Testing

- `bun test` for pure modules: scoring, retrieval ranking, key extraction, Jira
  payload mapping, markdown conversions, placeholder resolution.
- Service tests: the live services over in-memory drizzle on `bun:sqlite` (D15) and
  a stub `fetch` serving recorded Jira/Confluence responses from `src/test/fixtures`
  (`src/test/seed.ts` has the shared fixture routes). `scripts/mock-jira.ts` and
  `scripts/mock-confluence.ts` also serve end-to-end tests over real HTTP.
- LLM pipelines: schema tests with canned model outputs (scripted models); validation
  and repair paths tested with deliberately invalid outputs; a live eval
  (`src/test/eval`) that runs only when `SECRETARY_EVAL_*` variables are set.
- Model robustness: the replay harness (section 7.3) doubles as a regression test
  when prompts or schemas change; keep a small committed set of sanitised inbox
  items with expected proposals under `src/test/eval`.
- E2E: manual checklist per phase in `implementation-plan.md`; Playwright via
  tauri-driver is optional later.
